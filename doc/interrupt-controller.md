# Interrupt controller — primary-source cross-check

`hardware/src/intc.sail` (SSG-3, `doc/system-state-goals.md`) models the
interrupt controller as the **hardware that realizes the IPI mailbox** of
`machine.sail` (`Machine.ipi`, `deliver_ipi`/`receive_ipi`). It has three
per-core transitions:

| model | hardware stage | primary source |
|---|---|---|
| `intc_send` | originator's MMIO write latches the pending line | GIC SGI write (IHI 0069 §4.4); AIA `seteipnum_le` / per-hart IPI address |
| `intc_mask`/`intc_unmask` | per-interrupt enable/disable (`masked` = inverted `eie`) | GIC `GICR_ISENABLER0`/`GICR_ICENABLER0` (IHI 0069 §4.7.1); AIA `eie` array / `mie.MSIE` |
| `intc_enter_context`/`intc_exit_context` | per-hart delivery gate (interrupt context) | AIA `eidelivery` (IMSIC-reg-eidelivery) / `sstatus.SIE`; GIC CPU-interface interrupt enable |
| `intc_ack` | PE read clears pending for that PE only, rings the doorbell | GIC ICC_IAR ack (IHI 0069 §1.2 targeted-list, §2.2.1 1023); AIA `*topei` write |

This document is the 2026-08-18 primary-source cross-check against

- **Arm IHI 0069 H.b** — *Generic Interrupt Controller Architecture
  Specification*, GICv3/v4 (`~/Dokumente/IHI0069H_b_gic_architecture_specification.pdf`), and
- **RISC-V AIA** — *Advanced Interrupt Architecture*
  (`~/src/riscv-aia/src/{IPIs,IMSIC}.adoc`).

The model's **semantics** are confirmed correct on every stage; the cross-check
did surface four **citation/terminology imprecisions** in the Sail comments,
now corrected (see "Corrections" below). No semantic change: `intc.sail`
regenerates `hardware/rocq/intc.v` byte-identically.

## Stage-by-stage

### 1. `intc_send` — latch the pending line

The model sets `pending[i] := true` regardless of the mask — an edge-triggered
record of the interrupt.

- **GIC.** "SGIs are typically used for inter-processor communication, and are
  generated by a write to an SGI register in the GIC" (IHI 0069 **§4.4
  Software Generated Interrupts**, p. 4-60; a Group 1 SGI is written to
  `ICC_SGI1R_EL1`). Edge-triggered semantics: an edge-triggered interrupt "is
  asserted on detection of a rising edge of an interrupt signal and then,
  regardless of the state of the signal, remains asserted until the interrupt
  is acknowledged by software" (IHI 0069 **§1.2 Terminology**, *Interrupt
  types*). That "remains asserted … regardless of the state" is exactly the
  latch the model gives `intc_send` (pending recorded even if masked).
- **RISC-V.** Base privileged arch: "a machine with multiple harts must provide
  for each hart an implementation-defined memory address that can be written to
  signal a machine-level software interrupt" (AIA **IPIs.adoc**). With IMSICs,
  "an IPI can be sent to a hart by writing to the destination hart's IMSIC, the
  same as a regular message-signaled interrupt" (IPIs.adoc); the write port is
  `seteipnum_le` — "A write of the value i … to `seteipnum_le` (Set External
  Interrupt-Pending bit by Number) causes the pending bit for interrupt i to be
  set to one" (AIA **IMSIC.adoc**).

### 2. `intc_mask`/`intc_unmask` — per-PE enable/disable

The model sets/clears `masked[i]`; a masked interrupt stays pending but is not
signalled.

- **GIC.** "SGIs can be enabled and disabled by writing to **GICR_ISENABLER0**
  and **GICR_ICENABLER0** when affinity routing is enabled" (IHI 0069 **§4.7.1
  Enabling individual interrupts**). Because SGIs are per-PE (local to a CPU
  interface), the per-PE mask is the **Redistributor** `GICR_*ENABLER0`, not the
  Distributor `GICD_*` (which only gates legacy, distributor-level operation).
- **RISC-V.** The per-interrupt enable bits are the `eie` array ("Registers
  `eip0` through `eip63` contain the pending bits … `eie0` through `eie63`
  contain the enable bits for the same interrupt identities", AIA
  **IMSIC.adoc**); for the base software-interrupt mechanism the mask is the
  `mie.MSIE` bit (IPIs.adoc).

### 3. `intc_ack` — clear pending for *this PE only*, ring the doorbell

The model: if `pending[i] ∧ ¬masked[i]`, clear `pending[i]` and set `ipi[i]`
(the delivered bit `Machine.ipi` consumes); otherwise a spurious no-op.

- **GIC.** SGIs follow the **targeted list model**: "Multiple PEs receive the
  interrupt independently. When a PE acknowledges the interrupt, the interrupt
  pending state is cleared only for that PE. The interrupt remains pending for
  each PE independently until it has been acknowledged by the PE" (IHI 0069
  **§1.2 Terminology**, *Targeted list model*). This is exactly the model's
  per-PE pending semantics. Acknowledging with nothing pending returns INTID
  **1023** — "This value is returned in response to an interrupt acknowledge, if
  there is no pending interrupt" (IHI 0069 **§2.2.1 Special INTIDs**) — the
  masked/no-pending no-op case.
- **RISC-V.** The pending bit is cleared by the `*topei` CSR: "when a `*topei`
  CSR is written, if the register value has interrupt identity i in bits 26:16,
  then the interrupt file's pending bit for interrupt i is cleared" (AIA
  **IMSIC.adoc**). A zero value "has no effect" — the spurious no-op.

### 2.5 `intc_enter_context`/`intc_exit_context` — the per-hart delivery gate

The model splits the per-*interrupt* enable (`masked`, = inverted `eie` /
`GICR_ICENABLER0`) from the per-*hart* delivery gate (`delivery`). A hart in
interrupt context has `delivery = false`; a send still latches `pending`
(edge-triggered, §1 above), and the ack is a spurious no-op — the interrupt is
held pending, never dropped, never delivered early
(`intc_ack_in_context_noop`).

- **RISC-V.** "`eidelivery` … controls whether interrupts from this interrupt
  file are delivered from the IMSIC to the attached hart so they appear as a
  pending external interrupt in the hart's `mip` or `hgeip` CSR" (AIA
  **IMSIC-reg-eidelivery**; value **0 = delivery disabled**, 1 = enabled). The
  hart-level gate is also `sstatus.SIE` / `mie.MSIE` in the base Privileged
  Architecture.
- **GIC.** The per-hart gate is the CPU interface's interrupt enable / priority
  mask, distinct from the Redistributor's per-interrupt `GICR_ICENABLER0`.

This is the "no lost or duplicated shootdown" half of SSG-3: the remote enters
interrupt context to handle the shootdown IPI, holds any *second* shootdown
pending, and takes it only after leaving the context
(`test_vector_intc_exit_delivers`).

## The doorbell (`ipi[i] := true`) is `Machine.ipi`'s delivered bit

The model's `intc_ack` ring is exactly the mailbox bit `Machine.ipi` consumes:
`intc_proofs.v` proves `intc_send_ack_refines_deliver_ipi` (one send + ack is
`deliver_ipi`'s update) and `intc_delivery_enables_receive_ipi` (a
controller-produced mailbox flushes exactly core i via `ipi.v`). So the
GIC/AIA device stage refines the S2.3 mailbox on which the shootdown proof
rests.

## Corrections (comment-only, no semantic change)

The cross-check corrected four imprecise citations in `intc.sail`:

1. `IHI0069 2.1.2` (edge-triggered + per-PE pending) → **IHI 0069 §1.2
   Terminology** (there is no §2.1.2; §2.1 is "The Distributor and
   Redistributors").
2. `IHI0069 2.1.2` (SGI generation) → **IHI 0069 §4.4 Software Generated
   Interrupts** (p. 4-60).
3. `IHI0069 2.4.x` (mask) → **IHI 0069 §4.7.1 Enabling individual interrupts**,
   and `GICD_ISENABLER0`/`GICD_ICENABLER0` → **`GICR_ISENABLER0`/`GICR_ICENABLER0`**
   (SGIs are per-PE, so the mask is the Redistributor register).
4. IMSIC `setipnum` → **`seteipnum`** (Set External Interrupt-Pending bit by
   Number; `setipnum` is not a register in AIA).

Verified `sail --just-check` passes and `intc.v` regenerates byte-identically.

## Trust line

The interrupt-controller model is now cross-checked against both primary
specifications (Arm IHI 0069 H.b and RISC-V AIA). The model abstracts away the
parts Tessera does not yet reason about — groups/security state, the active
state and explicit deactivation (EOI), and distributor routing mode — and
records them here as deliberate omissions, not silent assumptions. Interrupt
**priority selection** (the `*topei` / ICC_IAR highest-priority pick) is now
modeled separately in `hardware/rocq/intc_priority.v` (below).

- **Active state / deactivation.** Real SGIs "have an active state and therefore
  require explicit deactivation" (IHI 0069 §1.2). The model collapses
  ack→deactivate into the single pending-clear: correct for the
  doorbell-delivery property, but not a model of interrupt nesting/priority.
- **Priority — now modeled.** `hardware/rocq/intc_priority.v` models the
  `*topei` / ICC_IAR selection as a pure function over the per-hart file: the
  *least* identity `i` such that `pending[i] ∧ enabled[i] ∧ (threshold = 0 ∨
  i < threshold)` ("interrupts with lower identity numbers have higher
  priorities", AIA IMSIC.adoc `*topei`; Arm ICC_IAR returns the INTID of the
  highest-priority pending interrupt above ICC_PMR/ICC_BPR). Proved:
  soundness (`topei_some_eligible`), minimality (`topei_minimal`),
  completeness (`topei_none_no_eligible`), and priority over lower identities
  (`topei_priority`), plus `vm_compute` vectors. The shootdown-IPI doorbell
  (one pending bit) does not exercise this, so the `intc.sail` reification is
  unaffected.
- **Groups & security state.** No group (Group 0/1) or security-state
  distinction; `intc_ack` takes any pending, unmasked, delivery-enabled
  interrupt. This is the SGI-IPI subset, not the full GIC.
- **Delivery ordering.** The model is sequential; the weak-memory ordering of
  the MSI/IPI write against the data it announces is the S2.4 concern
  (`shootdown_weak_broadcast.v`), left to that track, not to the device model.
