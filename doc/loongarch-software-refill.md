# Third MMU variant: LoongArch software-refill TLB

## Why this is the third variant

LoongArch shares variant 2's axis 1 (software refill — **no hardware page-table
walker**): a TLB miss traps to the OS, whose handler loads an entry
(`tlbwr`/`tlbwi`).  The trust-boundary win of `doc/mips-software-refill.md`
applies verbatim — "the MMU walks the table thus" becomes a theorem about *our*
refill handler (`la_refill_lookup_covers`).  What LoongArch contributes is a
**different realization of the page-size spectrum** (axis 2), exercised on a
second real architecture (telix targets `kernel/src/arch/loongarch64/`).

## Two LoongArch-specific features (vs MIPS)

| aspect | MIPS (`mips_tlb.sail`) | LoongArch (`loongarch_tlb.sail`) |
|---|---|---|
| page-size decode | PageMask run-of-1s, even count → `compute_mask_level` | **per-entry `ps` field** stored directly by the refill handler (`fill_tlb_entry`) |
| page size | `2^(base_shift + level)`, base = 10/12 (ESP) | `2^ps`, `ps` constrained by `CSR_PRCFG2` (`check_ps`) |
| entry granularity | one page | **odd/even pair** — one entry covers two adjacent pages |
| VPN field | VA[39:10] (30-bit), VPN2X = VA[12:11] | **VPPN = VA[47:13]** (35-bit) |
| match | `vpn[29..shift] == va[39..(10+shift)]` | `va[47:ps+1] == vppn[34:ps-12]` |
| PA | `pfn[43..level] @ va[ps-1:0]` | `pfn[35:ps-12] @ va[ps-1:0]`, `va[ps]` picks pfn0/pfn1 |
| physical width | 56 | 48 (PALEN); PPN = PTE[47:12] (36-bit) |

## Model shape (`hardware/src/loongarch_tlb.sail`)

Self-contained, parallel to `machine.sail`/`mips_tlb.sail`; the Rocq is
generated by `build.sh` into `loongarch_tlb.v`/`loongarch_tlb_types.v`.

- `LaEntry = { vppn : mword 35, ps : Z, pfn0 : mword 36, pfn1 : mword 36 }`.
- `la_vppn_of va = va[47..13]`.
- `la_covers e va` — page-size-aware VPN match over the odd/even pair,
  expressed with fixed-width shifts (place `vppn` at VA bits [13:47], shift
  both sides right by `ps+1`; Sail variable subranges are not first-class).
- `la_pa e va` — `pfn[35:ps-12] @ va[ps-1:0]`, with `va[ps]` selecting the
  even (pfn0) / odd (pfn1) half.
- `la_refill` / `la_flush` / `la_lookup` — the software refill handler, the
  software invalidation (QEMU `invalidate_tlb`), and the TLB lookup.

## Theorems proved (`loongarch_tlb_proofs.v`)

All axiom-free against the generated model:

1. **Refill-handler correctness** — `la_refill_lookup_covers`: refill-then-lookup
   is the entry's translation when the entry covers the address (the
   trust-boundary win).
2. **Shootdown integration** — `la_flush_clears` /
   `la_unmap_without_flush_breaks_coherence` / `la_refill_flush_composes` /
   `la_shootdown_correct` are the LoongArch twins of variant 1's
   coherence/shootdown theorems.
3. **14 `vm_compute` vectors** — VPPN extraction, 4 KiB/16 KiB odd/even
   coverage (both halves and the next-pair rejection), 4 KiB-vs-16 KiB
   non-coverage, PA translation (odd/even × 4 KiB/16 KiB), refill and flush.

## QEMU differential oracle (`loongarch_qemu_oracle.v`)

Hand-transcribed from QEMU's loongarch64 TCG (`target/loongarch/{tcg/tlb_helper,
cpu_helper}.c` on the `nadia.chambers/page-grain-001` branch) — there is **no
upstream Sail model**, so QEMU's TCG is the only oracle.  The oracle uses
*different* expressions from the model so the agreement genuinely exercises the
transcription:

- `qemu_la_match` — `loongarch_tlb_search_cb`'s pair match
  (`(va[47:0] >> (ps+1)) == zero_extend(vppn >> (ps+1-13), 48)`), vs the model's
  `(va[47:0] >> (ps+1)) == (vppn << 13 >> (ps+1))`.
- `qemu_la_odd` / `qemu_la_pfn` — `loongarch_map_tlb_entry`'s `n = (addr >> ps) & 1`.
- `qemu_la_pa` — `loongarch_check_pte`'s `((pfn & ~((1<<(ps-12))-1)) << 12) |
  (va & ((1<<ps)-1))`, vs the model's `(pfn >> (ps-12)) << ps | va[ps-1:0]`.

11 executable diff vectors pin match/PA agreement on both halves of the 4 KiB
and 16 KiB pairs and the next-pair rejections, plus the odd/even selection.  The
general `shiftr (shiftl x 13) (ps+1) = shiftr x (ps+1-13)` bitvector identity
(which would give the unconditional `la_covers_conforms`) is a noted follow-up;
the vectors pin the agreement concretely.
